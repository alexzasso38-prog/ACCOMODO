# Provider e comunicazioni

Stato: adapter SMTP/Twilio/Stripe implementati usando SDK ufficiali, contratti e firme testati localmente; **nessun account validato in sandbox, nessun provider attivato**. Prerequisiti: PREREQUISITES.md.

Fonti ufficiali consultate il 11 ottobre 2026: [Twilio Python SDK](https://github.com/twilio/twilio-python), [RequestValidator](https://github.com/twilio/twilio-python/blob/main/twilio/request_validator.py), [Messaging](https://www.twilio.com/docs/messaging), [WhatsApp templates](https://www.twilio.com/docs/whatsapp/tutorial/send-whatsapp-notification-messages-templates), [Stripe Python SDK](https://github.com/stripe/stripe-python), [Stripe Connect direct charges](https://docs.stripe.com/connect/direct-charges), [webhook signatures](https://docs.stripe.com/webhooks/signature). Le README ufficiali SDK sono state lette da GitHub; le pagine dei portali provider sono riferimenti per la successiva validazione, non prove di chiamate sandbox. Con il SDK bloccato Stripe 12.1.0 si usa `client.checkout.sessions`, non la superficie `client.v1` introdotta nelle versioni più recenti. Twilio 9.5.2 usa `TwilioHttpClient(timeout=10)`.

SMTP impone STARTTLS; Message-ID stabile non garantisce deduplica del server. WhatsApp usa content_sid e content_variables e richiede opt-in/template approvato. Nessun outbound è usato per dedurre una finestra inbound di assistenza. SMS è distinto e facoltativo; il fallback umano del simulatore è esplicito, non inventa un recapito mobile per numeri nascosti.

Outbox transazionale PostgreSQL; Celery tick ogni 30 secondi, SET LOCAL per tenant, claim SKIP LOCKED, lock di sede prima dell'outbox. Retry con backoff fino a 5 tentativi, errore permanente su recapito/opt-in/quote. Chiave evento = prenotazione+versione+tipo. Reminder default 24 ore prima, quiet hours 22–09: anticipato all'ultima ora consentita; per prenotazioni tardive si usa soltanto la conferma immediata. Modifica/cancellazione invalidano il precedente reminder. COMPLETED, NO_SHOW o fine servizio sopprimono code arretrate. DB e template consentono solo booking_link/received/confirmed/changed/cancelled/rejected/reminder/payment_due: nessuna tipologia survey/review/post_visit.

La demo registra Notification `simulated` e consumi `_simulated` non fatturabili. Non conserva il contenuto completo dei messaggi. Il pannello mostra lo stato dell'outbox. Non viene promessa consegna exactly-once: in reale un timeout dopo accettazione provider deve portare a `uncertain` e riconciliazione con provider ID, non reinvio cieco. Il dispatch reale resta bloccato proprio perché replay, mapping dei callback e riconciliazione non sono stati validati. `/api/webhooks/{provider}` risponde 503 anche con env compilate: nessun payload client può attivare incasso o invio.

Stripe Connect adapter usa account connesso esplicito nelle options e chiave idempotente, non la piattaforma come collettore di incassi di terzi. Non conserva carte. In demo un solo Payment per prenotazione, webhook/evento simulato deduplicato, conferma soltanto dopo pagamento, scadenza libera risorse; pagamento tardivo è rifiutato senza incasso. Rimborso completo simulato unico, nessun addebito da no-show. L'adapter refund non è un sistema commerciale di rimborsi verificato.

Il provider vocale fase 2 è un Protocol configurabile; tool bridge con routing di sede iniettato dal server, riepilogo esplicito, durata/costo massimo e handoff. Nessun LLM ha accesso al DB o genera disponibilità/allergeni. Le telefonate AI e audio recording sono disattivate. La lista attesa è disponibile via API con consenso email e HOLD reale 5 minuti, non con invii reali automatici.
